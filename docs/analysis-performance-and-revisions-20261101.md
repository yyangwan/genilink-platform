## 2. 多模块下拉不生效

审计洞察、平台差异对照、品牌发现对比共用 `setTaskScope`。旧代码调用：

```ts
window.history.replaceState(window.history.state, '', url);
```

Next.js 16.2.6 在内部历史状态中保存 `__NA`。其 history 桥接逻辑遇到带 `__NA` 的参数，会当作框架内部操作跳过 URL 状态通知。因此浏览器地址变化了，`useSearchParams` 仍保留旧值。自定义 `genilink-task-scope` 事件只通知部分自建订阅者，不能通知 Next 的 hook。

修复采用 Next 自带指南中的外部 history API 用法：

```ts
window.history.replaceState(null, '', url);
```

Next 自行保留内部路由状态并通知 `useSearchParams`，无需额外请求整份分析。

原测试把 `useSearchParams` 模拟成也订阅自定义事件，掩盖了实际问题。修正测试模型后，旧代码 4 项测试失败，修复后通过。新增用例覆盖自有品牌、对比品牌、目标平台、需求场景与显示分数同步，并确认不重新请求分析详情。

另用真实 Next.js 16.2.6 和 Chromium 的独立小页面验证：旧调用复现地址／画面不一致；调用实际修复后的 helper，四项选择全部同步。临时验证文件保留在工作目录的 `.tmp-scope-smoke/`，未加入源码提交。

## 3. 一次审计为什么有多个修订

### 三种不同的版本

- **审计 audit**：一次采集任务，固定问题与平台范围。
- **分析修订 Run revision**：针对同一审计，在某个输入状态下生成的分析快照。界面“审计 99 · 修订 3”中的修订属于这一层。
- **行动任务修订**：人工修改行动方案、材料和验收条件产生的独立任务版本，与分析修订不是同一计数。

### 生成过程

1. `ingestion.prepare_run` 锁定所属项目的审计，冻结 manifest：已经入库的回答、来源及正文版本、品牌与实体身份、别名／提及归属、问题评价范围等。
2. 对 manifest 计算 `input_hash`，另计算分析算法／模型配置的 `signature`。
3. 同一审计已有相同输入哈希与分析签名时，复用原 Run；反复点击“启动分析”并不必然产生新修订。符合条件的最新失败任务可重试原 Run。
4. 输入或分析签名有变化时，取该审计已有最大 revision 加一，创建分析任务。唯一约束与审计锁保证修订号及输入去重。
5. 后台处理后发布为 `ready` 或 `partial`，并以单调递增方式更新已发布修订指针，防止较早任务晚完成后覆盖较新结果。

### 哪些变化会带来新修订

- 回答陆续封存入库，或来源正文补采成功后，触发增量刷新。
- 实体身份确认、别名／提及归属、问题评价范围审核等变更会请求刷新。
- 项目品牌配置同步后，旧快照可能失效；后续重新分析会冻结新配置。
- 模型／分析规则签名变化后重新分析，也会形成不同版本。
- 人工证据审核另有审核记录，不应把每次审核动作都理解为新建 Run。

增量刷新不是每收到一条来源就立即跑一遍：默认有 **60 秒合并窗口**；处理中间增强默认 **每 24 小时最多 3 次**，到限可等待下一窗口。新版对全部采集和来源输入已终止的最终汇总有例外，避免最终结果被中间增强额度阻塞。部署配置可以覆盖这些默认值。

例如：修订 1 基于先取得的回答生成部分结果；来源正文随后补齐，修订 2 加入可核验证据；身份或问题分类确认后，修订 3 按新输入重算。三者属于同一次审计，不代表又重新向所有平台提问三轮。未变化文本可复用语义分析缓存，新输入仍可能消耗分析资源。

### 用途与使用建议

- 保存当时依据，让报告、具体行动及复测基线指向确定的 Run，而非不断变化的结果。
- 保留历史，解释分数变化究竟来自补齐证据、纠正归属还是新一轮采集。
- 对旧依据标记过期，避免把旧事实或旧身份当作当前行动依据。
- 日常优先看最新可用修订，同时留意“部分完成／快照过期”。同一审计修订之间的分数变化不能直接当作市场效果改善；效果观察应发起独立复测。
