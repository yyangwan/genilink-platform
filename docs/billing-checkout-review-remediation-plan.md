## 1. 文档目标

本文档记录独立收银台、优惠与自动续费实现与技术规格之间的差异，并给出可以直接拆分开发任务的修复方案。

整改目标：

- 保证渠道订单、结算会话和订阅状态一致，避免已付款但未开通。
- 保证微信支付和支付宝支付回调具备严格、统一的财务校验。
- 保证优惠券预占、切换、核销和周期优惠计算准确。
- 保证自动续费在渠道能力未完成时不会被错误展示为可用。
- 保证续费任务可重试、可接管、可对账，并正确执行宽限期。
- 消除幂等键跨用户复用和结算会话信息泄露风险。
- 建立可阻断发布的类型检查、代码规范和关键链路测试门禁。

## 2. 总体结论

当前实现完成了统一收银台、服务端报价、支付方式切换、优惠基础模型和续费任务基础模型，但还不能认为完整实现了原技术规格。

| 模块 | 当前状态 | 上线判断 |
|---|---|---|
| 独立统一收银台 | 已实现 | 修复支付过期问题后可用 |
| 微信、支付宝单次支付 | 部分完成 | 暂不满足安全上线条件 |
| 优惠活动与优惠券 | 部分完成 | 修复并发与统计后可用 |
| 自动续费签约 | 仅有接口和数据模型 | 不得对外开放 |
| 自动续费扣款 | 仅有调度框架 | 不得对外开放 |
| 续费失败与宽限期 | 部分完成 | 权限行为与方案不一致 |
| 财务回调校验 | 部分完成 | 必须补齐金额、币种和身份校验 |
| 工程质量门禁 | 未通过 | 类型检查和 lint 必须恢复 |

## 3. 严重级别和上线标准

| 级别 | 定义 | 发布要求 |
|---|---|---|
| P0 | 可造成批量错误扣款、资损或不可逆数据破坏 | 必须立即阻断所有相关功能 |
| P1 | 可造成付款未开通、错误计费、越权或续费状态错误 | 全部修复后才能发布 |
| P2 | 工程质量、可维护性或非主链路体验问题 | 原则上随本次整改完成 |

本次审查没有确认到已经发生的 P0 事故，但存在多项可能引发资损或付款未开通的 P1 风险。

## 4. 问题与修复方案

### 4.1 P1：渠道订单有效期没有与结算会话对齐

#### 问题

结算会话有效期为 30 分钟，但微信 Native 下单没有设置 `time_expire`，支付宝网页支付没有设置 `timeout_express`。本地过期任务只把结算会话标记为 `expired`，没有可靠关闭所有未完成的渠道订单。

用户在本地会话过期后仍可能完成支付。回调处理尝试把 `expired` 会话转换成 `completed` 时会失败，形成“渠道已扣款、系统未开通订阅”的异常订单。

微信关单实现还存在协议错误：当前使用 `DELETE` 和查询参数，微信支付 API v3 要求使用 `POST`，并通过 JSON 请求体传递 `mchid`。支付宝关单目前为空实现。

涉及代码：

- `src/lib/billing/gateways.ts`
- `src/lib/billing/checkout/service.ts`
- `src/lib/billing/payments/wechatpay.ts`
- `src/lib/billing/payments/alipay.ts`
- `src/lib/billing/reconcile.ts`

#### 修复方案

1. 创建渠道订单时，将渠道过期时间设置为结算会话的 `expiresAt`。
2. 微信 Native 下单增加 `time_expire`，使用 RFC 3339 时间并包含时区。
3. 支付宝网页支付增加 `timeout_express`，建议使用与剩余会话时间一致的分钟数，并限制最小值。
4. 修正微信关单为 `POST /v3/pay/transactions/out-trade-no/{out_trade_no}/close`，请求体为 `{ "mchid": "..." }`。
5. 实现支付宝 `alipay.trade.close`。
6. `expireStaleSessions` 只负责原子更新本地状态；新增可重试的关单任务处理所有 `pending/processing` 支付尝试。
7. 关单失败不能回滚本地过期状态，应记录重试次数、下次执行时间和最后错误。
8. 对迟到的成功回调建立明确策略：先查询渠道最终状态；如果确认已支付，则进入异常支付队列，由系统补开通或退款，不能持续返回 500。

#### 验收标准

- 收银台过期后二维码或支付链接不能继续完成付款。
- 过期任务能够关闭同一会话下全部未支付渠道订单。
- 重复执行关单任务不报错，渠道返回“订单已关闭或已支付”时按最终状态处理。
- 模拟迟到成功回调时，回调接口稳定返回确认结果，并生成可追踪的异常支付记录。

#### 必测场景

- 微信订单在会话过期前、过期后支付。
- 支付宝订单在会话过期前、过期后支付。
- 一个会话先创建微信订单，再切换支付宝，过期后两个订单都被处理。
- 关单请求超时后重试。
- 本地先过期、渠道随后返回成功回调。

### 4.2 P1：自动续费能力被声明为可用，但渠道实现未完成

#### 问题

微信和支付宝适配器可以根据环境变量返回 `recurring: true`，但签约、查约、解约和扣款方法仍抛出 `notConfigured`。收银台只创建本地 `PaymentAgreement` 待签约记录，没有发起渠道签约，也没有签约回调将协议变为 `active`。

此外，到期前 7 天和 3 天通知、渠道解约失败后的后台重试也尚未实现。

涉及代码：

- `src/lib/billing/payments/wechatpay.ts`
- `src/lib/billing/payments/alipay.ts`
- `src/lib/billing/payments/orchestrator.ts`
- `src/lib/billing/renewals/service.ts`

#### 修复方案

本项分为“安全降级”和“完整实现”两阶段。

安全降级阶段：

1. 微信和支付宝适配器固定返回 `recurring: false`。
2. 后端拒绝客户端提交 `autoRenew=true`，返回明确的 `RECURRING_NOT_AVAILABLE`。
3. 前端不展示自动续费选项，并说明当前为手动续费。
4. 不允许仅通过环境变量将未实现能力切换为可用。

完整实现阶段：

1. 分别确定微信委托代扣、支付宝周期扣款的签约产品和审批状态。
2. 实现 `createAgreement`、`queryAgreement`、`revokeAgreement` 和 `chargeAgreement`。
3. 新增独立签约回调路由，严格验证签名、商户身份和协议号。
4. 只有渠道协议状态确认有效后，才能把 `PaymentAgreement.status` 更新为 `active` 并开启 `Subscription.autoRenew`。
5. 实现解约后台重试任务，禁止用 `pending` 同时表达“待签约”和“解约失败”。建议增加 `revoking` 状态。
6. 实现 T-7、T-3 通知任务及幂等通知记录。
7. 完成沙箱和真实商户环境验证后，才允许适配器返回 `recurring: true`。

#### 验收标准

- 渠道能力未实现或未审批时，任何页面和 API 都不能开启自动续费。
- 签约成功、签约拒绝、用户取消、协议失效和主动解约均有确定状态转换。
- 解约接口失败时，本地立即停止未来扣款，并由后台继续尝试渠道解约。
- 同一协议不会被重复签约、重复扣款或重复通知。

### 4.3 P1：续费支付回调没有进入续费对账流程

#### 问题

续费订单的 `checkoutSessionId` 为空。当前 webhook 路由只有在订单包含 `checkoutSessionId` 时才调用新的对账函数，否则进入旧的一次性订阅激活逻辑。虽然 `reconcileCheckoutPayment` 内部已经支持按 `orderType=renewal` 转发，但路由层没有让续费订单进入该函数。

结果可能包括：

- `RenewalAttempt` 长期停留在 `processing`。
- 续费周期没有按续费规则更新。
- 支付事件和续费尝试之间缺少正确关联。

涉及代码：

- `src/app/api/billing/webhooks/[provider]/route.ts`
- `src/lib/billing/reconcile.ts`
- `src/lib/billing/renewals/service.ts`

#### 修复方案

1. webhook 路由按 `orderType` 分发，而不是仅按 `checkoutSessionId` 判断。
2. `orderType=renewal` 直接调用统一对账入口，由其进入 `reconcileRenewalPayment`。
3. 仅历史订单且确实没有新领域模型关联时，才允许进入 legacy 路径。
4. 对未知 `orderType`、缺失关联的订单记录告警并标记事件为 `requires_review`，不能静默激活订阅。
5. 为一次购买、升级、手动续费和自动续费建立参数化路由测试。

#### 验收标准

- 自动续费成功回调后，支付订单、续费尝试、订阅周期和支付事件在同一事务中完成更新。
- 重复回调不会重复延长订阅周期。
- 回调处理失败后可安全重放。

### 4.4 P1：续费任务租约无法接管，异常任务会永久卡住

#### 问题

续费任务领取后状态被设置为 `processing`，但领取 SQL 只查询 `scheduled`。如果工作进程崩溃、调用渠道超时或支付回调丢失，即使 `lockedUntil` 已经过期，该任务也不会被其他工作进程接管。

`runRenewalBatch` 捕获异常后只记录 `skipped`，没有恢复任务状态或安排下一次重试。

涉及代码：

- `src/lib/billing/renewals/service.ts`

#### 修复方案

1. 领取条件同时覆盖到期的 `scheduled` 和租约过期的 `processing`。
2. 接管 `processing` 前必须先根据支付订单号查询渠道状态，避免原工作进程已成功提交扣款但本地尚未落库时重复扣款。
3. 给每次渠道扣款使用稳定幂等键，幂等键至少包含订阅、计费周期和重试序号。
4. 区分以下状态：`scheduled`、`processing`、`awaiting_confirmation`、`succeeded`、`failed`、`canceled`、`requires_review`。
5. 捕获执行异常后，根据错误类型安排重试或人工处理，不能只保留 `processing`。
6. 增加看门狗任务，扫描租约过期和长时间等待回调的尝试。

#### 验收标准

- 工作进程在领取任务后退出，租约过期后其他进程可以安全接管。
- 接管前查询到渠道已扣款时，只做本地对账，不再次扣款。
- 回调丢失时，系统可以通过主动查询完成最终对账。
- 所有卡住任务都有监控指标和可定位日志。

### 4.5 P1：周期优惠基价错误，导致续费重复折扣

#### 问题

首次购买时，系统把已经优惠后的 `renewalAmountCents` 保存为订阅的 `renewalPriceCents`。续费计算又从该金额中扣除优惠快照，导致折扣被应用两次。

例如标准价 100 元、连续八折：首次价格为 80 元，当前实现可能把 80 元保存为续费基价，再减去 20 元优惠，续费变成 60 元。

涉及代码：

- `src/lib/billing/checkout/quote.ts`
- `src/lib/billing/reconcile.ts`
- `src/lib/billing/renewals/service.ts`

#### 修复方案

1. 明确金额字段语义：
   - `standardPriceCents`：签约时套餐标准价。
   - `renewalBasePriceCents`：后续续费计算基价，v1 默认等于标准价。
   - `discountCents`：本期优惠金额。
   - `amountDueCents`：本期实际应付。
2. 订阅保存未折扣的续费基价，不保存已经优惠后的实际金额作为基价。
3. 优惠快照保存优惠类型、数值、适用期数、已使用期数和到期规则。
4. 每次续费从基价重新计算当期优惠，只应用一次。
5. 首期优惠结束后，下一期恢复基价；连续 N 期优惠严格执行 N 次。

#### 验收标准

- 首期优惠、永久优惠、连续 N 期优惠的每一期金额都与报价规则一致。
- 升级后重新建立的周期使用升级后的标准价和优惠快照。
- 金额计算全部采用整数分，不使用浮点数。

#### 必测场景

- 100 元首期八折，第二期恢复 100 元。
- 100 元连续三期八折，前三期各 80 元，第四期 100 元。
- 固定减免金额大于商品价格时最低为 0，不出现负数。
- 重试同一期续费时金额保持不变。

### 4.6 P1：优惠券修改与支付确认存在竞态，预占和上限统计不准确

#### 问题

应用和移除优惠券时没有锁定结算会话，也没有限定只能更新 `ready` 状态。支付确认可能已经按旧金额创建渠道订单，另一个请求随后又修改会话金额，最终导致回调金额不一致。

优惠券切换还存在以下问题：

- 移除优惠券没有同步释放已有预占。
- 切换优惠券时复用原兑换记录，但没有更新 `couponId`。
- 活动使用上限按单个优惠码统计，而规格中的上限属于 `Promotion`，多个优惠码可以绕过活动总上限。

涉及代码：

- `src/lib/billing/checkout/service.ts`
- `src/lib/billing/promotions/service.ts`
- `src/lib/billing/payments/orchestrator.ts`

#### 修复方案

1. 应用优惠、移除优惠和确认支付都在事务中先对 `CheckoutSession` 执行 `SELECT ... FOR UPDATE`。
2. 锁定后重新读取状态，只允许 `ready` 会话修改优惠。
3. 确认支付后立即把会话转换为不可修改价格的状态。
4. 切换优惠券时，先锁定旧兑换记录和新优惠券，再原子释放旧预占并创建或更新新预占。
5. 移除优惠券时同步释放 `reserved` 兑换记录，并恢复无优惠报价快照。
6. 活动总次数、用户次数和工作空间次数按 `promotionId` 统计；如产品需要单码上限，另增明确的 Coupon 级字段。
7. 只有成功支付事务可以把 `reserved` 转换为 `redeemed`。
8. 会话过期、取消和支付最终失败时释放预占；临时渠道错误不应立即释放仍有效会话的预占。

#### 验收标准

- 应用优惠和确认支付并发时，只能有一个操作成功改变价格状态。
- 切换 A 券到 B 券后，只能核销 B 券。
- 同一活动创建多个优惠码时，活动总上限不能被绕过。
- 重复确认支付、重复回调不会重复核销。

### 4.7 P1：宽限期与功能权限判断不一致

#### 问题

续费失败后订阅进入 `past_due` 并设置 7 天宽限期，但权限代码只把 `active` 和 `trialing` 视为有权限。因此用户第一次扣款失败后会立即失去付费功能，与“宽限期内继续使用”的产品规则冲突。

涉及代码：

- `src/lib/billing/renewals/service.ts`
- `src/lib/billing/access.ts`
- `src/lib/billing/guard.ts`

#### 修复方案

1. 统一实现 `isSubscriptionEntitled(subscription, now)`，所有 API、页面和配额检查共用该函数。
2. 权限规则：
   - `active`、`trialing`：允许访问。
   - `past_due` 且 `gracePeriodEnd > now`：允许访问，同时展示欠费提醒。
   - `past_due` 且宽限期已结束：拒绝付费功能。
   - `canceled`、`expired`、`unpaid`：拒绝付费功能。
3. 宽限期结束任务应幂等地更新最终状态并重新计算权限。
4. 不允许前端自行推断宽限期权限，后端返回统一的 entitlement 状态和原因。

#### 验收标准

- 扣款失败后的 7 天内，用户仍可以使用原套餐功能和剩余配额。
- 宽限期结束后权限被准确关闭。
- 宽限期内补缴成功后恢复 `active`，不会重置或重复延长周期。

### 4.8 P1：结算会话幂等键没有按所有者隔离

#### 问题

`CheckoutSession.idempotencyKey` 当前全局唯一。创建服务命中相同幂等键后，只比较请求摘要，没有验证原会话是否属于当前用户和工作空间。如果不同用户生成相同键且请求参数相同，可能返回其他用户的结算会话。

涉及代码：

- `prisma/schema.prisma`
- `src/lib/billing/checkout/service.ts`
- `src/app/api/billing/checkout-sessions/route.ts`

#### 修复方案

推荐使用数据库复合唯一约束：

```prisma
@@unique([userId, workspaceId, idempotencyKey])
```

同时执行以下校验：

1. 查询和唯一冲突恢复都必须使用用户、工作空间和幂等键。
2. 命中已有会话后仍要比较请求摘要；摘要不同返回 `IDEMPOTENCY_CONFLICT`。
3. API 返回会话前再次校验所有权。
4. 支付确认幂等键继续使用会话 ID 作为命名空间，不能退化成全局客户端键。
5. 日志中只记录幂等键摘要，不记录完整键。

#### 验收标准

- 不同用户使用相同幂等键时各自创建独立会话。
- 同一用户、同一工作空间、同一请求重复提交时返回同一会话。
- 同一作用域使用相同键但参数不同，返回 409 且不泄露原会话内容。

### 4.9 P1：支付成功回调缺少强制金额、币种和完整身份校验

#### 问题

统一渠道事件中的 `amountCents` 可以为空，没有统一的 `currency` 字段。当前逻辑只在金额存在时比较金额，相当于允许缺失金额的成功事件继续激活订阅。微信回调校验商户号，但没有同时验证 APPID。

涉及代码：

- `src/lib/billing/payments/provider.ts`
- `src/app/api/billing/webhooks/[provider]/route.ts`
- `src/lib/billing/reconcile.ts`
- `src/lib/billing/renewals/service.ts`

#### 修复方案

1. 成功事件必须解析出：渠道事件号、商户订单号、渠道交易号、商户身份、应用身份、金额、币种、支付状态和支付时间。
2. `VerifiedProviderEvent` 增加 `currency`，对成功事件将金额和币种改为必填。
3. 微信校验 `mchid` 和 `appid`，支付宝校验 `app_id`、`seller_id` 或配置中规定的收款主体。
4. 严格验证订单渠道、订单号、金额和币种。v1 只接受 `CNY`。
5. 缺失或不匹配时不得激活订阅，应把支付事件标记为 `rejected` 或 `requires_review` 并触发告警。
6. webhook HTTP 应答遵循渠道重试规则：可恢复的内部错误返回失败；永久校验失败避免无限重试，同时保留安全审计记录。

#### 验收标准

- 金额为空、币种错误、APPID 错误、商户号错误和订单渠道错误均不能激活订阅。
- 合法重复回调返回成功，但不重复更新订阅。
- 原始回调报文加密或脱敏存储，敏感字段不进入普通日志。

### 4.10 P1：生产数据库迁移可能与既有表结构冲突

#### 问题

涉及代码：

## 6. 统一状态机要求

### 6.1 结算会话

```text
ready
  -> processing
  -> completed

ready
  -> expired

processing
  -> completed
  -> expired / requires_review
```

约束：

- 只有 `ready` 可以修改优惠和支付方式。
- `processing` 后价格快照不可修改。
- `completed` 是终态，不允许再次创建支付尝试。
- `expired` 收到成功支付时进入异常对账，不允许简单报错退出。

### 6.2 支付订单

```text
pending
  -> processing
  -> paid
  -> failed
  -> closed
  -> requires_review
```

约束：

- 同一结算会话可以有多个支付尝试，但最多一个成功订单。
- 任何成功订单都必须通过金额、币种和商户身份校验。
- `paid`、`closed` 为终态，重复回调只做幂等确认。

### 6.3 续费尝试

```text
scheduled
  -> processing
  -> awaiting_confirmation
  -> succeeded
  -> failed
  -> canceled
  -> requires_review
```

约束：

- `processing` 租约过期后可以被接管。
- 接管前必须查询渠道状态。
- 同一订阅、同一周期、同一尝试序号只有一个扣款幂等键。
- 成功只能延长一次订阅周期。
